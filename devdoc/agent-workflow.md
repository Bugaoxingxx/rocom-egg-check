# Agent 文档阅读与维护流程

本流程适用于本仓库内的 agent 开发、维护和发布任务。README 中的 “For agent” 部分是入口；`devdoc/` 是项目开发文档的维护位置。

## 开始任务前

1. 阅读 `devdoc/` 中现有文档，至少包括项目简述、设计语言和本流程；根据任务范围继续阅读对应的代码、UI 说明、许可记录及发布说明。
2. 先检查当前实现和工作区状态。文档提供背景和约定，代码、配置与数据是当前行为的事实来源。
3. 明确本次改动会影响哪些已经记录的功能、结构、数据来源、设计约定或维护流程。

## 开发期间维护文档

1. 当代码、数据、界面、资源来源或开发与发布流程改变时，在同一任务中更新受影响的文档，不把已过时的说明留给后续维护者。
2. 将产品概况和代码路径写在 `project-overview.md`，视觉与交互约定写在 `design-language.md`，任务或流程细节放入对应专题文档。
3. 新增专题文档时，在 `project-overview.md` 的相关资料中添加链接；需要 agent 或开发者直接发现的流程，也在 README 中提供入口。
4. 只记录已由实现、配置或明确项目决定支持的内容。更新后检查术语、路径、文件名和链接，并移除与新行为冲突的旧说明。

## 完成与发布

1. 提交前对照改动检查文档是否准确、相关链接是否有效，以及新增流程是否已加入索引。
2. 纯文档任务按用户指示提交并推送，不需要运行应用打包，也不需要为了文档改动单独发布版本。
3. 应用发布前，先按 Conventional Commits 提交本次产品改动，确保工作区干净；`release.mjs` 需要干净工作区，并根据最新版本标签之后的提交计算版本。
4. agent 随后运行 `npm run release`，同步版本清单和 `CHANGELOG.md`；检查生成结果，提交版本改动并创建对应版本标签。随后按用户指示触发云端构建，确认构建成功后发布 GitHub Release 并上传产物。版本更新和 changelog 不交由用户手工处理。
